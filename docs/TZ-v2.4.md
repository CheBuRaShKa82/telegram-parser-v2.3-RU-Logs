Доработать текущий `v2.3` без переписывания проекта с нуля. Сохранить парсинг и инвайтинг, исправить найденные критические ошибки, сделать multi-account работу корректной, безопасной и восстанавливаемой после сбоев.

## 1. P0 — критические исправления

### 1.1. Единая модель пользователя
Проблема: парсер сохраняет ID как `user_id:access_hash`, а загрузчик инвайтера читает только строки `.isdigit()`. Кроме того, username и ID одного человека сейчас могут восприниматься как разные записи.

Требования:
- перестать использовать два независимых TXT-файла как основное хранилище очереди;
- добавить SQLite-таблицу пользователей;
- основной идентификатор пользователя — `user_id`;
- хранить минимум:
  - `user_id`
  - `username`
  - `first_name`
  - `last_name`
  - `source_id`
  - `source_title`
  - `source_type`
  - `parsed_at`
  - `last_seen_at`
- TXT/CSV оставить как экспорт/совместимость;
- не допускать дублей одного пользователя по username и ID.

### 1.2. Убрать перенос `access_hash` между аккаунтами
Проблема: `access_hash` зависит от Telegram-сессии и не должен использоваться другой сессией.

Требования:
- не хранить `InputPeerUser(user_id, access_hash)` как универсальную ссылку для всех аккаунтов;
- каждая сессия должна самостоятельно резолвить пользователя;
- приоритет резолва:
  1. entity/cache конкретной сессии;
  2. username;
  3. ID только если entity уже известна этой сессии;
- не использовать `access_hash`, полученный одной сессией, в другой.

### 1.3. Исправить target/entity для multi-session
Проблема: target entity, полученная одной сессией, переиспользуется другими.

Требования:
- хранить переносимый target reference:
  - публичный `@username`, если есть;
  - peer ID/ссылка только как идентификатор;
- каждая Telegram-сессия должна самостоятельно получать свой `InputEntity`;
- preflight и inviter не должны передавать entity одной сессии другой.

### 1.4. Переделать `excluded_users`
Проблема: ошибки, зависящие от target/session, сейчас могут глобально исключить пользователя.

Требования:
- разделить глобальные и scoped-исключения;
- создать сущность вида:
  - `user_id`
  - `session_file` nullable
  - `target_key` nullable
  - `reason`
  - `first_ts`
  - `last_ts`
  - `hits`
- глобально исключать только действительно глобальные причины;
- `user_kicked`, `not_mutual_contact`, ограничения конкретной цели и подобные ошибки не должны навсегда блокировать пользователя для других целей;
- исправить баг, где ошибка текущего инвайт-аккаунта может исключить приглашавшегося пользователя.

### 1.5. Защита секретов и runtime-файлов
Добавить `.gitignore` минимум для:
- `sessoins/`
- `*.session`
- `*.session-journal`
- `options.txt`
- `invite_ledger.db*`
- `app.log`
- `*.log`
- `usernames.txt`
- `userids.txt`
- `*.bak-*`
- `__pycache__/`
- `*.pyc`
- `.venv/`
- `venv/`

Дополнительно:
- по возможности создавать session-файлы с правами `0600` на Linux;
- не показывать полный `api_hash` в меню настроек;
- не использовать номер телефона как обязательное публичное имя session-файла/лога.

### 1.6. Обновить зависимости
Требования:
- обновить Telethon с `1.40.0` до актуальной стабильной совместимой версии;
- убрать уязвимый pin `pyasn1==0.6.1`;
- использовать безопасную версию `pyasn1>=0.6.4` либо позволить Telethon управлять транзитивной зависимостью;
- после обновления проверить все используемые RPC/errors на совместимость.

## 2. P1 — важные исправления логики

### 2.1. Retry одного пользователя на другой сессии
Проблема: при FloodWait/PeerFlood/network/blocked текущий пользователь часто теряется, а цикл переходит к следующему.

Требования:
- один пользователь должен иметь внутренний retry-loop;
- при временной ошибке текущей сессии пробовать следующую доступную сессию;
- `max_user_attempts` должен реально ограничивать число попыток одного пользователя за прогон;
- после исчерпания лимита фиксировать понятный статус.

### 2.2. Ошибка одной сессии не должна останавливать весь прогон
- `ChatAdminRequiredError`, auth failure и ограничения конкретной session должны выводить из работы только эту session;
- весь прогон останавливается только если:
  - нет доступных сессий;
  - цель глобально недоступна;
  - пользователь отменил работу.

### 2.3. Исправить `max_attempts_per_session`
Сейчас параметр фактически означает короткую паузу.

Нужно выбрать и реализовать одно:
- либо настоящее ограничение N попыток на session за запуск;
- либо переименовать параметр в `pause_every_n_attempts`.

Предпочтительно: настоящее ограничение + отдельная настройка planned rotation.

### 2.4. Восстановление session после исправления
- успешная авторизация должна снимать сохранённый `banned=True`;
- добавить понятное состояние:
  - active
  - temporary_blocked
  - flood_wait
  - peer_flood
  - unauthorized
  - disabled
- временные блокировки должны иметь срок окончания.

### 2.5. Корректное закрытие ресурсов
Все клиенты и SQLite connections должны закрываться через `try/finally`.

Исправить:
- ранний `return` в message parsing;
- ранний `return` при пустой очереди инвайта;
- `preflight_sessions_for_target()`;
- `inviting_rotate_sessions()`;
- Ctrl+C / KeyboardInterrupt.

### 2.6. Checkpoint парсинга
- не держать весь результат только в RAM до конца;
- сохранять найденных пользователей батчами;
- рекомендуемый batch: 100–500 пользователей;
- после сетевой ошибки/перезапуска уже найденные пользователи не теряются.

### 2.7. Статистика должна быть реальной
Исправить все счётчики:
- ok
- already
- privacy
- forbidden
- floodwait
- peerflood
- network
- invalid
- rpc_other
- other

Итоговый summary должен соответствовать реально произошедшим событиям.

### 2.8. Разделить state и event history
Сейчас `INSERT OR REPLACE` уничтожает предыдущую историю.

Создать:
- `invite_state` — текущее состояние user × target;
- `invite_events` — append-only история всех попыток.

Event минимум:
- timestamp
- user_id
- username
- target
- session
- status
- reason/error
- flood seconds при наличии.

## 3. Парсинг

### 3.1. Обычные группы/супергруппы
Сохранить режим `iter_participants()`.

Требования:
- корректная обработка FloodWait/permission errors;
- checkpoint;
- не терять результат при частичном сбое;
- логировать количество полученных/отфильтрованных/сохранённых.

### 3.2. Активные пользователи по сообщениям
Сохранить `iter_messages()`.

Требования:
- дедуп по `user_id`;
- настройки:
  - лимит сообщений;
  - максимальный возраст;
  - batch save;
- не считать этот режим «полным списком участников».

### 3.3. Каналы и комментарии
Добавить отдельный режим:
`Канал → посты → комментарии / linked discussion → авторы комментариев`.

Требования:
- получать связанную discussion-группу;
- собирать авторов комментариев/ответов;
- сохранять source как `channel_comments`;
- явно обозначить, что это активная аудитория, а не полный список подписчиков канала.

Предпочтительно:

- сохранять blocked_until в БД;
- не делать двойное ожидание Telethon + собственный scheduler.
